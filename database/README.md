# Database migrations (Alembic)

The Postgres schema is versioned with [Alembic](https://alembic.sqlalchemy.org/). The SQLAlchemy
models stay in `packages/seeing_db/seeing_db/models.py` (the API and the batch job import them);
this folder only holds the migration scripts.

```
database/
  alembic.ini              # script_location = migrations
  migrations/env.py        # connects with seeing_db.config.database_url(), compares with seeing_db.models.Base
  migrations/versions/     # one file per revision, numbered 0001_, 0002_, ...
```

The connection comes from `DATABASE_URL` (or `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` on Cloud Run).

## Everyday commands (from the repo root)

```bash
make migrate                       # alembic upgrade head (console script `seeing-migrate`)
make revision MSG="add places"     # new revision autogenerated from the models; review it before committing
cd packages/seeing_db && poetry run alembic -c ../../database/alembic.ini downgrade -1
cd packages/seeing_db && poetry run alembic -c ../../database/alembic.ini current
```

Rules:

- Change the models first, then generate a revision and **read it**: autogenerate misses enum
  changes, server defaults and data migrations. Keep `downgrade()` working.
- Never edit a revision that has been applied to a deployed database; add a new one.
- Name files `NNNN_short_description.py` with `revision = "NNNN"` so the history stays readable.

## Deployment

`seeing-migrate` finds `alembic.ini` through `$ALEMBIC_CONFIG` when set, otherwise in this folder of
the repository checkout. The web image copies this folder to `/app/database` and sets
`ALEMBIC_CONFIG=/app/database/alembic.ini`; `infra/scripts/deploy.sh` runs the Cloud Run job
`seeing-migrate-{env}` (`alembic upgrade head`) with the new image before deploying the service.
